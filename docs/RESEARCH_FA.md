بررسی در ۳ نوامبر ۲۰۲۶ از روی HEAD عمومی مخازن زیر انجام شد. این گزارش ادعای بررسی تمام GitHub یا تأیید بازاریابی همهٔ پروژه‌ها را ندارد. متن README کافی فرض نشد؛ مسیر اجرای پروب و کانفیگ در سورس خوانده شد.

## نتیجهٔ اصلی به زبان ساده

«مرورگر واکنش دید» با «کانفیگ واقعاً ترافیک عبور داد» یکی نیست. بعضی پنل‌ها اولی را پینگ یا IP سالم می‌نامند؛ NightLine این دو را جدا می‌کند:

1. رادار داخل صفحه نامزد پیدا می‌کند؛ نیازی به نصب ابزار تازه ندارد.
2. خروجی خودکار، در همان برنامهٔ مبتنی بر Xray که کاربر با آن وصل می‌شود، اتصال واقعی را آزمایش و مسیر پاسخگو را انتخاب می‌کند.

## رادار مرورگر در این نسخه

- برای هر مقصد TLS، تصویر و fetch به‌طور هم‌زمان و در سه نوبت اجرا می‌شوند.
- فقط پورت‌های TLS کلادفلر بررسی می‌شوند؛ درخواست HTTP از صفحهٔ امن دیگر ساخته نمی‌شود. پورت‌های دیگر از آزمون کنار گذاشته می‌شوند، نه از تنظیمات ذخیره‌شدهٔ کانفیگ.
- پیش از اسکن، HTTP پنل و سه آدرس کنترل `192.0.2.1`، `198.51.100.1` و `203.0.113.1` بررسی می‌شوند. این‌ها نمونهٔ IP سالم نیستند.
- کف واکنش از تأخیر پنل محاسبه می‌شود: ۴۰٪ پایه، محدود به ۲۰ تا ۲۰۰ میلی‌ثانیه. واکنش آنی زیر کف، نامزدِ سریع محسوب نمی‌شود.
- اگر آدرس کنترل نیز واکنش قابل‌ملاحظه داشته باشد، نامزد‌یابی حدسی قابل اتکا فرض نمی‌شود. تنها تکمیل واقعی fetch می‌تواند «پاسخ HTTP» باشد.
- برای نامزدشدن حداقل دو نوبت سیگنال لازم است؛ عدد نمایش‌داده‌شده «واکنش» است و قطعی‌بودن اتصال را اثبات نمی‌کند.
- رتبهٔ پاسخ HTTP و نامزد تخمینی جداست. اولویت‌بندی یا افزودن فقط با اقدام کاربر است و IPها خودکار حذف نمی‌شوند.
- لغو، مهلت و تعداد درخواست‌های هم‌زمان محدودند. handler و timer تصویر و fetch پس از پایان پاک می‌شوند.

این خودآزمایی احتمال خطای مثبت را کم می‌کند، نه اینکه دلیل TLS، فایروال، پراکسی و قطع شبکه را با قطعیت تشخیص دهد. هیچ اسکن از دیتاسنتر به جای اینترنت کاربر انجام نشده است.

## انتخاب واقعی در هستهٔ Xray

خروجی `?format=xray&profile=auto` این ساختار را می‌سازد:

- دامنهٔ خود پنل و حداکثر سه مقصد متمایز TLS از ابتدای فهرست ذخیره‌شده؛ فهرست **قبل از ساخت کانفیگ‌ها** محدود می‌شود تا هزینهٔ CPU روی Worker کنترل شود.
- VLESS در صورت فعال‌بودن آن؛ در غیر این صورت Trojan فعال. هیچ پروتکل خاموش‌شده‌ای به زور روشن نمی‌شود.
- سه الگو: `tlshello / 5-16 / 2-3`، `tlshello / 10-20 / 1-3` و `tlshello / 100-200 / 1-3`.
- `observatory.subjectSelector = ["nl-probe-"]` و URL `https://www.gstatic.com/generate_204`.
- `routing.balancers` با `leastPing`، انتخاب فقط از outboundهای آزمون، و fallback مشخص.
- دورهٔ آزمون پنج دقیقه؛ نخستین انتخاب نیز با هستهٔ واقعی تست شد و نیاز به صبر پنج‌دقیقه‌ای نداشت.
- بررسی گواهی TLS خاموش نیست؛ همهٔ خروجی‌های عمومی `allowInsecure:false` دارند.
- خروجی از قالب دیگری با نام auto برگردانده نمی‌شود؛ درخواست auto با قالب غیر Xray خطای روشن می‌گیرد.

این روش در برنامه اجرا می‌شود، نه در Worker و نه با دسترسی مرورگر به برنامهٔ محلی. ابزار محلی جدید یا اسکنر Python لازم نیست؛ **برنامه باید Xray و JSON کامل را پشتیبانی کند**. ورود به برنامه‌ای که JSON را به URI تبدیل می‌کند می‌تواند قابلیت observatory/balancer را از بین ببرد. نتیجهٔ داخلی هسته خودکار به پنل گزارش داده نمی‌شود؛ پنل به جای آن عدد یا وضعیت ساختگی نمایش نمی‌دهد.

پروفایل هنگام فعال‌بودن تا ۱۲ مسیر را هر پنج دقیقه می‌آزماید؛ ترافیک و سهمیه مصرف می‌کند. اگر همهٔ مسیرها خراب باشند، fallback هم تضمین اتصال نیست. آزمون 204 نیز آزمون کامل آپلود طولانی یا همهٔ انواع DPI نیست.

## مشاور چه چیزهایی را دیگر انجام نمی‌دهد؟

شکست یک سرویس بیرونی یا آپلود کوتاه، بهانهٔ تغییر Early Data، DNS، طول Fragment یا IPهای ذخیره‌شده نیست. این حدس‌ها حذف شدند. پیشنهاد محدود سازگاری WS، در صورت وجود شواهد، فقط بعد از تأیید ذخیره می‌شود. خروجی خودکار به جای تغییر سراسری و حدسی تنظیمات، انتخاب واقعی را در کلاینت انجام می‌دهد.

آزمون HTTP داخل تونل کاربر و echo وب‌سوکت همچنان جدا هستند؛ اولی 2xx/3xx می‌خواهد، دومی فقط سلامت مسیر WS پنل را نشان می‌دهد. مشاهدات بیرونی در بخش بازشدنی قرار دارند و «فیلتر قطعی» اعلام نمی‌شوند.

## آزمون واقعیِ انتخاب خودکار

باینری رسمی Xray Linux نسخهٔ 26.10.31 استفاده شد. شانزده JSON تولیدی با هسته اعتبارسنجی شدند. سپس خود باینری با کانفیگ انتخاب خودکار اجرا شد:

1. مسیر اول و fallback عمداً خراب بودند؛ فقط آخرین مسیر کار می‌کرد.
2. لبهٔ TLS/WS و مقصد HTTPS آزمایشی، روی loopback با CA مخصوص تست قرار داشتند.
3. observatory باید از داخل VLESS یا Trojan به مقصد HTTPS می‌رسید؛ پاسخ سادهٔ وب‌سایت جایگزین نشد.
4. درخواست از HTTP proxy واقعی هسته، پس از انتخاب مسیر سالم پاسخ درست گرفت.
5. این آزمون جداگانه برای **VLESS و Trojan** موفق شد؛ دورهٔ پنج‌دقیقه‌ای خروجی حفظ و بررسی گواهی روشن بود.

این آزمایش انتخاب واقعی هسته و ساختار کانفیگ را تأیید می‌کند، نه عبور از فیلترینگ اپراتور کاربر. حساب Cloudflare کاربر و اینترنت ایران در این محیط قابل آزمایش نبودند.
